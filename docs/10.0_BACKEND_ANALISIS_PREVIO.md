# 5. Análisis por bloque solicitado

## 5.1 Ciclo de vida de una petición

```
Cliente ──▶ Nginx ──▶ Gunicorn ──▶ Flask app
                                    │
                                    ▼
                              Middleware (request_id, rate limit, seguridad, CORS)
                                    │
                                    ▼
                              Router / Blueprint
                                    │
                                    ▼
                              Controlador (route handler)
                                    │
                                    ▼
                              Validación de entrada (schema)
                                    │
                                    ▼
                              Servicio de negocio
                                    │
                                    ▼
                              Repositorio / Integración externa
                                    │
                                    ▼
                              Modelo ORM / Base de datos
                                    │
                                    ▼
                              DTO de salida
                                    │
                                    ▼
                              Middleware de respuesta (envoltura, headers, log)
                                    │
                                    ▼
                               Cliente
```

### 5.1.1 Bootstrap de la aplicación

Antes de atender la primera petición, la aplicación sigue este orden de arranque:

```
app.py / application factory
    ↓
Carga configuración desde core/config (según FLASK_ENV)
    ↓
Inicializa logging estructurado
    ↓
Inicializa SQLAlchemy (db)
    ↓
Inicializa migraciones (Migrate)
    ↓
Inicializa gestión de sesiones (Flask-Session)
    ↓
Inicializa protección CSRF
    ↓
Inicializa rate limiting (Flask-Limiter)
    ↓
Registra Blueprints (api/v1/public, api/v1/admin, api/v1/seo)
    ↓
Registra manejadores globales de errores
    ↓
Registra middleware (request_id, logging, headers de seguridad)
    ↓
Servidor listo
```

**Reglas del bootstrap.**

1. Ninguna extensión se inicializa fuera de la factory.
2. La configuración se valida antes de que cualquier extensión se configure; si falta un valor obligatorio, la aplicación no arranca (`CFG-02`).
3. Los blueprints se registran después de las extensiones pero antes de los manejadores de error.
4. El registro de middleware ocurre al final para que envuelva toda la aplicación.

**Puntos fijos que no pueden variar:**

- Nginx termina TLS y decide si la petición va a archivos estáticos, imágenes, API JSON (`/api/v1/*`) o SEO (`/_seo/*`) (`AD-04`).
- Cada petición recibe un `request_id` único en el middleware; viaja en `meta.request_id` y en logs (`OA-09`).
- El rate limiting se aplica antes de autenticación en API pública y después en panel (`03_SEGURIDAD.md` §14).
- La autenticación de panel lee la cookie `session` (`AD-37`); la API pública es anónima salvo revalidación.
- La autorización ocurre en el controlador o en un decorador que invoca al servicio de autorización.
- Los errores se traducen en el manejador global a la envoltura `AD-16`; los detalles técnicos no llegan al cliente (`03_SEGURIDAD.md` §16).

## 5.2 Responsabilidades por capa

| Capa | Responsabilidad | Puede | No puede |
|---|---|---|---|
| **`api/` (rutas/controladores)** | Recibir HTTP, extraer parámetros, invocar servicios, devolver respuesta HTTP | Validar presencia de campos mediante schema, llamar a servicios, manejar autorización de ruta | Tocar modelos, repositorios ni base de datos; contener reglas de negocio (`AD-03`) |
| **`schemas/`** | Validación estructural de entrada: tipos, longitudes, formatos, obligatoriedad | Usar Marshmallow/Pydantic; declarar campos, tipos, obligatoriedad | Contener lógica de negocio; acceder a base de datos |
| **`validators/`** | Validación de negocio reusable (no reglas de agregado complejas) | Validar invariantes simples, formatos de negocio | Acceder a base de datos; decidir reglas de agregado (`RN-xx`) |
| **`services/`** | Aplicar reglas de negocio (`RN-xx`), orquestar repositorios, construir DTOs de salida, abrir transacciones, llamar integraciones | Usar repositorios, integraciones, `core`, otros servicios, validators | Conocer HTTP ni schemas de salida; tocar modelos directamente |
| **`repositories/`** | Consultar y persistir agregados | Usar modelos SQLAlchemy y utilidades de `core` | Contener reglas de negocio; recibir DTOs; usar otros repositorios o servicios |
| **`models/`** | Estructura de datos del ORM | Definir tablas, columnas, relaciones, restricciones | Importar de `api`, `services`, `repositories`, `dtos`, `mappers` |
| **`dtos/`** | Estructuras de salida de la API | Ser construidos por mappers desde modelos/servicios | Contener lógica de negocio; depender de ORM; conocer modelos |
| **`mappers/`** | Convertir modelos ORM en DTOs y viceversa | Conocer modelos y DTOs | Contener lógica de negocio; acceder a base de datos |
| **`integrations/`** | Adaptar servicios externos (WhatsApp, futuros) | Usar clientes HTTP y traducir fallos a `IntegrationError` (`ERR-06`) | Exponer detalles del proveedor al resto del sistema |
| **`core/`** | Configuración, excepciones base, seguridad base, logging, utilidades transversales, auditoría | Ser importado por cualquier capa | Depender de `api`, `services`, `repositories`, `models`, `dtos`, `mappers` |
| **`infrastructure/`** | Detalles técnicos de persistencia y almacenamiento | Proveer clientes de base de datos, almacenamiento de archivos, conectores externos futuros | Contener lógica de negocio; ser importado por `services` directamente (salvo abstracciones) |

**Reglas de oro.**

1. Si una función en `services/` necesita importar `flask.request`, está mal ubicada.
2. Los `services/` son la **única** capa que puede abrir transacciones, coordinar repositorios, aplicar `RN-xx` y llamar integraciones.
3. Los `repositories/` nunca reciben DTOs; reciben IDs, entidades o parámetros simples.
4. Los `dtos/` nunca conocen SQLAlchemy; los `models/` nunca conocen DTOs. Solo los `mappers/` unen ambos mundos.

### Dependencias prohibidas

| Origen → Destino | Razón |
|---|---|
| `Controller` → `Repository` ❌ | La ruta no accede a datos directamente (`AD-02`). |
| `Controller` → `Model` ❌ | Los modelos no deben filtrar a la API (`AD-12`). |
| `Service` → `Model` ❌ | El servicio habla con repositorios, no con el ORM directamente. |
| `Repository` → `Service` ❌ | La dependencia es unidireccional. |
| `Repository` → `DTO` ❌ | Los repositorios reciben IDs, entidades o parámetros simples. |
| `Model` → `Repository` ❌ | Los modelos no conocen la capa de acceso a datos. |
| `Model` → `DTO` ❌ | Solo los mappers unen ambos mundos. |
| `DTO` → `Model` ❌ | Los DTOs no conocen SQLAlchemy. |
| `DTO` → `Repository` ❌ | Los DTOs son salida de la API, no argumentos de persistencia. |
| `Schema` → `Model` ❌ | La validación de entrada no depende del ORM. |
| `Core` → cualquier capa de negocio ❌ | `core/` es la capa más interna; no puede depender del exterior. |
| `Infrastructure` → `Service` / `Repository` (implementaciones) ❌ | La infraestructura es detalle técnico; no orquesta negocio. |

## 5.4 Jerarquía de excepciones

```
AppException (base, abstracta)
├── ValidationError              → 400 / 422
│   └── RequestValidationError   → 422 (esquema de entrada)
├── AuthenticationError          → 401
├── AuthorizationError           → 403
├── NotFoundError                → 404
├── BusinessRuleError            → 409
│   └── ConcurrencyError         → 409 (conflicto por actualización concurrente)
├── RateLimitError               → 429
├── IntegrationError             → 502
└── InternalError                → 500
```

**Reglas de mapeo a la envoltura `AD-16`:**

| Excepción | HTTP | Código en `errors[].code` | Campo adicional |
|---|---|---|---|
| `ValidationError` | `422` | `validation_error` | `field` cuando aplica |
| `RequestValidationError` | `422` | `validation_error` | `field` |
| `AuthenticationError` | `401` | `authentication_error` | — |
| `AuthorizationError` | `403` | `authorization_error` | — |
| `NotFoundError` | `404` | `resource_not_found` | `resource` |
| `BusinessRuleError` | `409` | `business_rule_violation` | `rule` (el `RN-xx`) |
| `ConcurrencyError` | `409` | `conflict` | — |
| `RateLimitError` | `429` | `rate_limit_exceeded` | `retry_after` |
| `IntegrationError` | `502` | `integration_error` | `provider` |
| `InternalError` | `500` | `internal_error` | — |

**Reglas `ERR-01` a `ERR-06` de `02_ARQUITECTURA.md` §9.11:**

- `ERR-01`: toda excepción conocida hereda de `AppException`.
- `ERR-02`: el manejador global traduce `AppException` a la envoltura uniforme; cualquier otra excepción se registra como `InternalError` con `request_id`.
- `ERR-03`: `BusinessRuleError` siempre expone el `RN-xx` violado en `errors[].rule`.
- `ERR-04`: `ValidationError` expone el campo problemático cuando existe.
- `ERR-05`: `IntegrationError` oculta detalles del proveedor; solo devuelve `provider` y código genérico.
- `ERR-06`: fallos externos nunca se propagan tal cual; se traducen a `IntegrationError`.

## 5.5 Middleware esencial

| Middleware | Orden | Responsabilidad | Origen |
|---|---|---|---|
| `RequestIdMiddleware` | 1 | Generar o propagar `X-Request-Id`; almacenar en `g.request_id`. | `OA-09` |
| `SecurityHeadersMiddleware` | 2 | Agregar headers de seguridad que dependan de la petición (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, CSP si es dinámica). | `03_SEGURIDAD.md` §12 |
| `RequestLoggingMiddleware` | 3 | Log de entrada/salida: método, ruta, status, duración, `request_id`, IP. | `03_SEGURIDAD.md` §15 |
| `RateLimitMiddleware` / Flask-Limiter | 4 | Aplicar límites por endpoint (`03_SEGURIDAD.md` §14). | `RNF-11` |
| `SessionMiddleware` / Flask-Session | 5 | Gestionar cookie de sesión en rutas `/api/v1/admin/*`. | `AD-37` |
| `CSRFMiddleware` | 6 | Validar token CSRF en métodos de escritura del panel. | `03_SEGURIDAD.md` §8 |
| `ErrorWrapperMiddleware` | 7 (último) | Capturar excepciones, invocar manejador global, devolver envoltura `AD-16`. | `AD-16` |

**Nota sobre headers estáticos.** `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` y `Permissions-Policy` se configuran preferentemente en Nginx. El middleware solo complementa lo que dependa del request (por ejemplo, CSP con `nonce` si se usara).

## 5.6 Configuración por entorno

**Decisión `AD-11`**: solo `core/config` lee variables de entorno. `10_BACKEND.md` debe materializar esto así:

```python
# core/config/base.py
import os

class BaseConfig:
    SECRET_KEY = os.environ.get('SECRET_KEY')
    SQLALCHEMY_DATABASE_URI = os.environ.get('DATABASE_URL')
    SQLALCHEMY_TRACK_MODIFICATIONS = False
    SESSION_TYPE = 'sqlalchemy'
    SESSION_SQLALCHEMY_TABLE = 'sessions'
    PERMANENT_SESSION_LIFETIME = 43200  # 12 horas
    WTF_CSRF_ENABLED = True

class DevelopmentConfig(BaseConfig):
    DEBUG = True
    TESTING = False

class TestingConfig(BaseConfig):
    TESTING = True
    SQLALCHEMY_DATABASE_URI = os.environ.get('TEST_DATABASE_URL', 'sqlite:///:memory:')
    WTF_CSRF_ENABLED = False

class ProductionConfig(BaseConfig):
    DEBUG = False
    TESTING = False
```

**Reglas `CFG-01` a `CFG-05` de `02_ARQUITECTURA.md` §9.12:**

- `CFG-01`: solo `core/config` lee variables de entorno.
- `CFG-02`: configuración se valida al arrancar; falta un valor obligatorio → la aplicación no arranca.
- `CFG-03`: se distinguen tres niveles: negocio (`store_settings`), entorno (variables) y constantes de código.
- `CFG-04`: configuración de negocio editable por administrador vive en base de datos, no en `.env`.
- `CFG-05`: valores sensibles nunca se loguean.

**Variables obligatorias para arrancar:**

| Variable | Entornos | Uso |
|---|---|---|
| `SECRET_KEY` | Todos | Firma de sesiones y tokens CSRF. |
| `DATABASE_URL` | Todos | Conexión PostgreSQL. |
| `TEST_DATABASE_URL` | Testing | Base de datos de pruebas. |
| `UPLOAD_FOLDER` | Todos | Ruta base de imágenes. |
| `LOG_LEVEL` | Todos | Nivel de log. |

## 5.8 Transacciones y concurrencia

**Reglas de transacción:**

1. **Unidad de trabajo por servicio.** Cada operación de escritura en un servicio corre dentro de una transacción SQLAlchemy. Si la operación invoca a varios repositorios, todos comparten la misma sesión.
2. **Decorador `@transactional`.** Vive en `core/decorators/transactional.py`. Se aplica a métodos de servicio de escritura.
3. **No transacciones en lectura.** Las operaciones de lectura no abren transacción explícita; usan `autocommit` o `session.execute` según el patrón del proyecto.
4. **Manejo de concurrencia optimista.** Para entidades que pueden editarse concurrentemente (precios, stock futuro), se usa `updated_at` como token de versión. El servicio verifica que el `updated_at` recibido coincida con el almacenado; si difiere, lanza `ConcurrencyError` → `409`.
5. **Lectura repetible en operaciones críticas.** El cálculo de promociones vigentes y la generación de slugs usan aislamiento adecuado para evitar condiciones de carrera.

**Flujo típico de escritura:**

```
ruta ──▶ schema.validate() ──▶ servicio.create_or_update()
                                  │
                                  ▼
                           @transactional inicia tx
                                  │
                                  ▼
                           repositorio.save(modelo)
                                  │
                                  ▼
                           auditoría.registrar()
                                  │
                                  ▼
                           tx.commit() o rollback() en excepción
```

## 5.9 Política de caché v1: No Cache

**Decisión `BK-06`.** En v1 no se implementa caché de aplicación (Redis/memoria). La estrategia de rendimiento se basa en:

1. **Índices de base de datos** para consultas frecuentes (búsqueda, filtros, slugs).
2. **Nginx como cache de archivos estáticos e imágenes** (`AD-04`).
3. **Respuestas JSON sin cache del lado del servidor.** Cada petición resuelve el estado actual.
4. **Headers de control de caché:**
   - API JSON pública: `Cache-Control: no-store, no-cache, must-revalidate`.
   - API JSON privada: `Cache-Control: no-store, private`.
   - Imágenes y estáticos: gestionados por Nginx con `expires` y `etag`.

**Justificación.** El catálogo es pequeño, la carga principal son imágenes, y agregar caché de aplicación introduce invalidaciones que en v1 no están justificadas (`PA-11`). El punto de extensión queda documentado para cuando el volumen lo requiera.

## 5.10 Logging y observabilidad

### Niveles de log

| Nivel | Uso | Ejemplo |
|---|---|---|
| `DEBUG` | Información de desarrollo; desactivado en producción. | Traza de una consulta compleja. |
| `INFO` | Eventos normales de la aplicación. | Petición HTTP completada. |
| `WARNING` | Situaciones anómalas pero recuperables. | Login fallido, rate limit cercano. |
| `ERROR` | Fallos que requieren atención. | Excepción no controlada, integración caída. |

### Sistemas de observabilidad separados

| Sistema | Responsabilidad | Destino | Origen |
|---|---|---|---|
| **Logs** | Eventos técnicos y diagnóstico. | Archivo/stdout estructurado. | `OA-09`, `03_SEGURIDAD.md` §15 |
| **Audit** | Operaciones de escritura del panel con contexto de negocio. | Tabla `audit_logs` inmutable. | `AD-20` |
| **Metrics** | Métricas de uso, rendimiento y salud. | Reservado para v2 (punto de extensión). | `OA-09` |
| **Tracing** | Trazabilidad distribuida de peticiones. | Reservado para v2 (punto de extensión). | `OA-09` |

> **AUDIT no es un nivel de log.** Es un sistema independiente que persiste quién hizo qué, cuándo y desde dónde.

**Principios de logs:**

1. **Toda petición tiene `request_id`.** Se genera en el middleware y se propaga a logs y respuestas.
2. **Estructura JSON en producción.** Cada línea incluye `timestamp`, `level`, `request_id`, `user_id`, `message`, `extra`.
3. **No datos sensibles.** Nunca se loguean contraseñas, hashes, tokens CSRF, números de tarjeta ni datos personales.

**Eventos de seguridad a loguear (`03_SEGURIDAD.md` §15):**

| Evento | Destino |
|---|---|
| Login exitoso | `audit_logs` |
| Login fallido | logs + `audit_logs` |
| Cambio de contraseña | `audit_logs` |
| CRUD de entidades | `audit_logs` |
| Subida de imagen | `audit_logs` |
| `403`, `401`, `429` | logs de aplicación |

## 5.12 Testing por capa

| Capa | Tipo de test | Alcance | Herramientas |
|---|---|---|---|
| `models/` | Unitario | Validación de constraints, relaciones, factory methods. | pytest, base de datos en memoria o test container. |
| `schemas/` | Unitario | Validación de entrada, mensajes de error, casos límite. | pytest + schema library. |
| `repositories/` | Unitario/Integración leve | Consultas y persistencia contra base de datos real de pruebas. | pytest, test container PostgreSQL. |
| `services/` | Unitario | Reglas de negocio con repositorios mockeados. | pytest + unittest.mock. |
| `api/` | Integración | Endpoints completos: status, envoltura, autenticación, rate limiting. | pytest + Flask test client. |
| `integrations/` | Integración | Adaptadores con mocks o servidores de prueba. | pytest + responses/VCR. |
| `core/` | Unitario | Configuración, excepciones, utilidades. | pytest. |

**Reglas de tests:**

1. Cada test de servicio usa un repositorio fake o mockeado; no levanta base de datos salvo que sea necesario.
2. Los tests de API no tocan servicios reales; mockean la capa de servicios para probar contrato HTTP.
3. Los tests de integración con base de datos usan una base aislada y se ejecutan en contenedor.
4. Los tests de integración externa nunca llaman al proveedor real en CI.
5. La cobertura mínima objetivo es 80% en servicios y 70% en repositorios.

## 5.13 Validadores: estructural vs. negocio

| Tipo | Vive en | Responsabilidad | Ejemplo |
|---|---|---|---|
| **Validación estructural** | `schemas/` | Tipos, longitudes, formatos, rangos, obligatoriedad. | `price` debe ser entero ≥ 1. |
| **Validación de negocio reusable** | `validators/` | Invariantes simples que no requieren base de datos ni deciden `RN-xx`. | Validar formato de SKU, verificar que `sale_price < list_price`. |
| **Validación de agregado** | `services/` | Reglas que requieren estado del dominio, contexto o coordinación. | `RN-31`, `RN-68`, `RN-70`: decidir si una marca puede eliminarse. |

**Reglas.**

1. `schemas/` nunca accede a base de datos.
2. `validators/` nunca accede a base de datos; solo encapsula cálculos o formatos.
3. Las reglas que dependen del estado actual del sistema (por ejemplo, "¿existe?", "¿tiene relaciones?") viven en `services/`.

## 5.14 Eventos internos (reservado)

En v1 no se implementa un bus de eventos. Sin embargo, se documentan los eventos de dominio identificados para reservar el patrón (`PA-12`):

- `ProductCreated`
- `ProductUpdated`
- `ProductActivated` / `ProductDeactivated`
- `PriceChanged`
- `PromotionActivated` / `PromotionDeactivated`
- `BannerPublished`
- `ImageUploaded` / `ImageDeleted`

**Propósito.** Cuando el sistema crezca, estos eventos permitirán desacoplar reacciones (reindexación, notificaciones, invalidación de caché) sin reescribir servicios.

**Reglas para v1.**

1. Los servicios implementan las reacciones de forma síncrona dentro del mismo método.
2. No se crea infraestructura de publicación/suscripción.
3. Los nombres de eventos se reservan y se documentan en `10_BACKEND.md`.

## 5.15 Estrategia de migraciones

Aunque las migraciones las ejecuta Alembic, `10_BACKEND.md` debe documentar el flujo oficial:

```
Modelo en código (SQLAlchemy)
    ↓
Generar migración con Alembic (autogenerate + revisión manual)
    ↓
Aplicar upgrade en entorno local
    ↓
Verificar esquema local contra producción (estructura y semillas)
    ↓
Ejecutar tests de integración
    ↓
Aplicar upgrade en producción con backup previo
    ↓
Verificar consistencia post-migración
```

**Reglas.**

1. Nunca se edita una migración ya aplicada en otro entorno.
2. Toda migración de datos destructivos requiere backup y rollback validado.
3. Antes de considerar una tarea finalizada, el esquema local debe coincidir con el de producción (`04_BASE_DATOS.md` §5).
4. Las migraciones se versionan en `migrations/versions/`.

# 6. Decisiones de implementación propuestas

## BK-01 — Un repositorio por agregado, sin repositorio genérico universal

| Campo | Valor |
|---|---|
| **Identificador** | `BK-01` |
| **Título** | Cada agregado de negocio tiene su propio repositorio explícito |
| **Contexto** | `AD-14` organiza el backend por capas con módulos por dominio. Sin una regla clara, puede surgir un `BaseRepository` genérico que oculte consultas específicas y termine acumulando lógica de filtrado en servicios. |
| **Decisión** | Se crea un repositorio por agregado (`ProductRepository`, `BrandRepository`, `CategoryRepository`, etc.). Puede existir una clase base muy ligera para sesión/CRUD mínimo, pero **no** un repositorio genérico universal. Las consultas específicas viven en el repositorio que las necesita. |
| **Consecuencias** | Los servicios no construyen consultas SQL ni filtros complejos. Cada repositorio es rastreable a un dominio. El costo es más archivos; el beneficio es que la capa de acceso a datos no se convierte en un cajón de sastre. |

## BK-02 — Un servicio por agregado funcional, con servicios transversales especializados

| Campo | Valor |
|---|---|
| **Identificador** | `BK-02` |
| **Título** | Los servicios se organizan por agregado funcional y operaciones transversales |
| **Contexto** | `AD-03` exige que toda regla de negocio viva en servicios. Si un servicio crece demasiado o si se crea un servicio por endpoint, la capa de negocio se vuelve difícil de probar y mantener. |
| **Decisión** | Se crea un servicio por agregado funcional: `ProductService`, `BrandService`, `CategoryService`, `PromotionService`, `AdministratorService`, etc. Además, existen servicios especializados para preocupaciones transversales: `AuthService`, `AuditService`, `ImageService`, `CatalogService` (consultas de catálogo público que cruzan agregados), `CartService` (revalidación). |
| **Consecuencias** | Las reglas `RN-xx` se agrupan naturalmente. Los servicios transversales no contienen reglas de dominio puro; orquestan agregados. Evita servicios gigantes y evita la proliferación de servicios de un solo método. |

## BK-03 — Un Blueprint por agregado

| Campo | Valor |
|---|---|
| **Identificador** | `BK-03` |
| **Título** | Cada agregado de negocio expone sus rutas a través de un Blueprint propio |
| **Contexto** | Un único blueprint gigante para todo el panel o todo el catálogo dificulta encontrar endpoints, aplica middleware de forma indiscriminada y complica la autorización por recurso. |
| **Decisión** | Se crea un blueprint por agregado: `products_bp`, `brands_bp`, `categories_bp`, `promotions_bp`, `administrators_bp`, `banners_bp`, `auth_bp`, `cart_bp`. Cada blueprint se registra en `api/v1/public/` o `api/v1/admin/` según su ámbito. |
| **Consecuencias** | La autorización y los prefijos de ruta se aplican por blueprint. Los endpoints de un dominio viven juntos. El costo es más registros; el beneficio es claridad y control granular. |

## BK-04 — Tamaño de servicio como señal de revisión

| Campo | Valor |
|---|---|
| **Identificador** | `BK-04` |
| **Título** | Un servicio que supera aproximadamente 400–500 líneas es una señal de revisión arquitectónica |
| **Contexto** | Un servicio grande suele acumular responsabilidades de varios subdominios, lo que dificulta las pruebas y aumenta el riesgo de cambios. |
| **Decisión** | **No es un límite rígido.** Si un servicio supera las 400–500 líneas, se debe revisar si contiene múltiples responsabilidades y si conviene dividirlo en servicios más pequeños o extraer utilidades/validators. |
| **Consecuencias** | Mantiene la cohesión de los servicios. Evita servicios monolíticos dentro de la capa de negocio. |

# 7. Backend Anti-Patterns

| Anti-patrón | Síntoma | Prevención en Pablito Sports |
|---|---|---|
| **Fat Controller** | La ruta valida reglas de negocio, lanza excepciones de dominio o construye DTOs complejos. | La ruta solo extrae parámetros, valida schema y delega al servicio. |
| **Repository genérico universal** | Un `BaseRepository` con métodos `find`, `filter`, `paginate` genéricos que fuerzan a los servicios a conocer detalles de consulta. | `BK-01`: repositorios específicos por agregado. |
| **Servicio por endpoint** | `CreateProductService`, `UpdateProductService`, etc. | `BK-02`: servicio por agregado funcional. |
| **Lógica de negocio en el ORM** | Validaciones o reglas en `sqlalchemy.event` o métodos de modelo que ocultan reglas. | `AD-03`: reglas en servicios; modelos solo estructuran datos. |
| **Fuga de HTTP en servicios** | `request` o `jsonify` importados desde `services`. | Prohibición explícita; los servicios deben poder ejecutarse desde un script. |
| **Excepciones crudas al cliente** | Devolver stacktraces, mensajes de biblioteca o detalles de SQL. | Jerarquía de excepciones + manejador global + `03_SEGURIDAD.md` §16. |
| **Caché preventiva** | Agregar Redis "por si acaso" antes de medir. | `BK-06`: No Cache en v1; optimizar por índices y Nginx. |
| **Configuración dispersa** | Variables de entorno leídas en módulos sueltos. | `AD-11` + `CFG-01`: solo `core/config` lee variables. |
| **Transacciones largas** | Una transacción abarca lecturas innecesarias o llamadas externas. | `@transactional` solo en escritura; integraciones nunca dentro de la transacción. |
| **Mockar solo lo fácil** | Tests de servicio que levantan base de datos innecesariamente. | Repositorios mockeados en tests de servicio; base de datos solo en tests de repositorio y API. |
| **Doble fuente de verdad de sesión** | Estado de sesión en cookie + JWT + memoria al mismo tiempo. | `AD-37`: solo sesión de servidor con cookie; nada más. |
| **Validación solo en el frontend** | El backend confía en que el cliente ya validó. | El backend valida siempre; el frontend solo anticipa por UX (`AD-03`). |
| **Repository que recibe DTO** | El repositorio recibe `CreateProductDTO` en lugar de parámetros simples o entidades. | `BK-01`: los repositorios reciben IDs, entidades o parámetros simples. |
| **Mapper con lógica de negocio** | El mapper decide reglas de visibilidad o descuentos al construir un DTO. | Los mappers solo transforman estructuras; las reglas las aplica el servicio. |
| **Servicio gigante** | Un servicio acumula reglas de varios subdominios y supera 500 líneas. | `BK-04`: revisar y dividir en servicios más cohesionados. |
| **Confundir log con audit** | Registrar eventos de negocio críticos solo en logs de aplicación. | Audit es un sistema separado; las escrituras del panel van a `audit_logs`. |
