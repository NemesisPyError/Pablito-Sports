# 2. Objetivo

Verificar la coherencia completa entre:

- `04_BASE_DATOS.md` (modelo físico aprobado),
- `05_API.md` (contrato de la API aprobado),
- `02_ARQUITECTURA.md` y `02.1_DECISIONES_ARQUITECTONICAS.md` (decisiones arquitectónicas),
- `01_ANALISIS_NEGOCIO.md` (reglas de negocio).

El propósito es detectar huecos, campos sin respaldo en el modelo, operaciones mal mapeadas o estados inconsistentes **antes** de escribir `06_FRONTEND.md` y comenzar la implementación del backend.

---

# 3. Alcance y método

## 3.1 Incluye

1. **Trazabilidad de campos DTO**: cada campo de cada DTO se mapea a tabla, columna y regla/decisión de origen.
2. **Revisión CRUD administrativa**: para cada endpoint de escritura se identifican tablas modificadas, tablas consultadas, generación de auditoría, historial de precios, soft delete y restauración.
3. **Matriz única de estados del sistema**: estados posibles de Producto, Variante, Promoción, Banner e Imagen.
4. **Compatibilidad futura de DTOs**: evaluación de si los DTOs actuales soportan extensiones probables de v2 sin romper compatibilidad.
5. **Casos extremos**: ~30 escenarios con respuesta esperada de la API y comportamiento del frontend.

## 3.2 No incluye

- Rediseño de decisiones arquitectónicas.
- Detalle de implementación de frontend o panel.
- Controles de seguridad específicos (están en `03_SEGURIDAD.md`).

## 3.3 Criterio de aprobación

La revisión se considera exitosa si:

- Todo campo de DTO tiene origen en el modelo físico.
- Toda operación de escritura tiene auditoría (`AD-20`).
- Todo cambio de precio tiene historial (`RN-70`).
- Los estados del sistema son los mismos en backend y frontend.
- Los casos extremos tienen respuesta API y comportamiento React definidos.

## 7.2 DTOs críticos para v2

### `ProductDetailDTO`

- **Compatible:** sí. Puede crecer con campos opcionales (`attributes`, `reviews`, `variants` con stock, etc.).
- **Riesgo:** si en v2 se cambia la estructura de `variants` de array plano a un agrupamiento por algún otro eje, los clientes v1 seguirían funcionando mientras se mantenga el array plano.

### `VariantDTO`

- **Compatible:** sí. `availability` ya prepara el terreno para stock por variante. Se puede añadir `stock_quantity`, `sku`, `barcode` opcionales.

### `ProductListItemDTO`

- **Compatible:** sí. Campos opcionales como `rating`, `badges` pueden agregarse.

### `CartRevalidationResultItem`

- **Compatible:** sí. `availability` puede pasar a reflejar stock por variante. Nuevos estados como `out_of_stock` a nivel variante son compatibles con la enumeración `status`.

### `PromotionDTO`

- **Compatible con precaución.** `scope` como objeto único es suficiente hoy. Para promociones múltiples en v2 se puede añadir `scopes[]` mientras se conserva `scope`.

## 7.3 Hallazgos de compatibilidad

**Hallazgo CF-01:** Los DTOs actuales soportan las extensiones más probables de v2 mediante campos opcionales adicionales.

**Hallazgo CF-02:** El único punto que requeriría cuidado es `PromotionDTO.scope`: si en v2 una promoción puede aplicar a varias entidades simultáneamente, el contrato deberá evolucionar manteniendo compatibilidad (por ejemplo, campo `scope` legacy + `scopes[]` nuevo).

**Hallazgo CF-03:** La ausencia de `id` en DTOs públicos (salvo `VariantDTO`) facilita la evolución del modelo sin cambiar el contrato.

# 8. Casos extremos

Se documentan 30 escenarios que cruzan estado del backend, respuesta de la API y comportamiento esperado del frontend. El objetivo es que React no interprete estados distintos a los que el backend comunica.

## 8.1 Carrito y revalidación

### CE-01 — Producto oculto mientras el carrito está abierto

- **Estado previo:** El cliente tiene una variante en el carrito. El administrador desactiva el producto (`is_active = false`).
- **Llamada API:** `POST /api/v1/cart/revalidate`
- **Respuesta API:** `status: "product_hidden"`, `product: null`.
- **Comportamiento React:** Eliminar el ítem del carrito y mostrar mensaje: "Este producto ya no está disponible."

### CE-02 — Producto eliminado lógicamente

- **Estado previo:** Variante en carrito; administrador hace soft delete del producto.
- **Llamada API:** `POST /api/v1/cart/revalidate`
- **Respuesta API:** `status: "product_deleted"`, `product: null`.
- **Comportamiento React:** Eliminar ítem e informar.

### CE-03 — Variante eliminada

- **Estado previo:** Variante en carrito; administrador elimina la variante (o quita el talle del producto).
- **Llamada API:** `POST /api/v1/cart/revalidate`
- **Respuesta API:** `status: "variant_removed"`, `product: null`.
- **Comportamiento React:** Eliminar variante y solicitar nueva selección de talle.

### CE-04 — Precio cambia una vez antes de enviar WhatsApp

- **Estado previo:** `list_price` o `sale_price` cambian.
- **Llamada API:** `POST /api/v1/cart/revalidate`
- **Respuesta API:** `status: "price_changed"`, nuevo precio en `list_price` / `sale_price`.
- **Comportamiento React:** Actualizar precio, mostrar aviso y bloquear envío hasta confirmación (`RN-77`, `RN-78`).

### CE-05 — Precio cambia dos veces antes de enviar WhatsApp

- **Estado previo:** Dos cambios de precio entre revalidaciones.
- **Llamada API:** `POST /api/v1/cart/revalidate`
- **Respuesta API:** Último precio vigente, `status: "price_changed"`.
- **Comportamiento React:** Mostrar el precio actual y aviso. El cliente confirma una sola vez sobre el estado más reciente.

### CE-06 — Promoción expira

- **Estado previo:** Producto tenía descuento por promoción; la promoción vence.
- **Llamada API:** `POST /api/v1/cart/revalidate`
- **Respuesta API:** `status: "sale_ended"`, `sale_price: null`, `discount_percentage: null`.
- **Comportamiento React:** Recalcular total, informar y pedir confirmación.

### CE-07 — Producto pasa a "sin stock" mientras está en el carrito

- **Estado previo:** `availability` cambia a `out_of_stock`.
- **Llamada API:** `POST /api/v1/cart/revalidate`
- **Respuesta API:** `status: "availability_changed"`, `availability: "out_of_stock"`.

## 9.3 Recomendaciones para 06_FRONTEND.md

1. **React debe tratar `cart_content_version` como parte inmutable del estado del carrito**, incrementándola en cada mutación y descartando respuestas obsoletas.
2. **El estado del carrito nunca debe actualizarse en silencio:** toda discrepancia detectada en revalidación requiere confirmación antes de generar el mensaje de WhatsApp (`RN-77`, `RN-78`).
3. **Los filtros deben serializarse en el orden canónico de `AD-27`** para URLs deterministas.
4. **Las facetas deben provenir siempre de `meta.facets`**; no calcularse en el cliente.
5. **Los DTOs públicos no incluyen `id` salvo `VariantDTO`:** React no debe depender de `id` para keys en listados públicos.
