Este documento es el análisis previo de `12_DEPLOY.md`. **No redacta el documento final**, sino que:

1. Define la topología de despliegue y la estrategia de release.
2. Establece el orden de despliegue seguro y las reglas de migración expand/contract.
3. Especifica health checks, smoke tests y criterios de éxito/rollback.
4. Documenta backups, variables de entorno, observabilidad y seguridad de despliegue.
5. Cierra decisiones operativas pendientes (`AP-01`, `ADP-04`, `ADP-13`).
6. Propone decisiones de implementación de despliegue (`DPL-xx`) sin introducir arquitectura nueva.

El resultado debe permitir redactar `12_DEPLOY.md` en una única pasada coherente.

# 4. Topología de despliegue

```
Internet
   │
   ▼
[ Nginx ]
   │
   ├──▶ Build React (estáticos: /, /catalogo, /producto/:slug)
   │
   ├──▶ Imágenes (/uploads/*)
   │
   ├──▶ API (/api/v1/*) ──▶ Gunicorn ──▶ Flask
   │                              │
   │                              ▼
   │                         [ PostgreSQL ]
   │
   └──▶ SEO (/_seo/*) ──▶ Gunicorn ──▶ Flask
```

**Componentes.**

| Componente | Tecnología | Rol |
|---|---|---|
| Frontend | React build estático | Aplicación de catálogo y panel. |
| Proxy / servidor de archivos | Nginx | TLS, estáticos, imágenes, proxy a API y SEO (`AD-04`). |
| Servidor de aplicación | Gunicorn | Ejecutar Flask en múltiples workers. |
| Backend | Flask | API JSON y endpoints SEO. |
| Base de datos | PostgreSQL | Persistencia. |
| Almacenamiento de imágenes | Volumen persistente | Archivos de imágenes fuera del contenedor (`AD-05`). |
| Certificados TLS | Let's Encrypt / proveedor | HTTPS obligatorio (`RNF-12`). |

# 5. Estrategia de despliegue

## 5.1 Alternativas evaluadas

| Estrategia | Estado | Razón |
|---|---|---|
| **Blue/Green** | ❌ Descartada | Requiere el doble de infraestructura y complejidad de BD sincronizada. No justificada para una sola instancia. |
| **Canary** | ❌ Descartada | Requiere tráfico dividido y métricas avanzadas. Sobredimensión para v1. |
| **Rolling** | 🟡 Reservada para v2 | Posible cuando haya múltiples instancias y health checks maduros. |
| **Recreate** | ✅ Elegida para v1 | Simple, predecible y suficiente para una sola instancia. El downtime breve es aceptable fuera de horario comercial. |

## 5.2 Recreate en v1

1. Detener tráfico nuevo (mantenimiento).
2. Backup verificado.
3. Aplicar migraciones compatibles.
4. Desplegar nueva versión.
5. Health checks.
6. Smoke tests.
7. Habilitar tráfico.

---

# 6. Orden de despliegue

```
1. Backup verificado de BD e imágenes
        ↓
2. Aplicar migraciones de base de datos (expand/contract)
        ↓
3. Desplegar backend (Gunicorn + Flask)
        ↓
4. Verificar health checks del backend
        ↓
5. Desplegar frontend (build estático)
        ↓
6. Recargar configuración de Nginx
        ↓
7. Ejecutar smoke tests
        ↓
8. Habilitar tráfico / quitar mantenimiento
        ↓
9. Observar métricas durante 15–30 minutos
```

**Reglas.**

- Nunca se despliega frontend antes de verificar que el backend responde correctamente.
- Las migraciones se aplican antes del despliegue de la aplicación.
- Si un paso falla, se detiene el proceso y se evalúa rollback.

# 7. Expand / Contract

## 7.1 Reglas de migración segura

| Prohibición | Razón |
|---|---|
| **No renombrar columnas en una sola release.** | El código anterior sigue leyendo el nombre viejo. Usar: añadir columna nueva → migrar datos → actualizar código → eliminar vieja en release posterior. |
| **No eliminar columnas usadas por código activo.** | Rompe la versión anterior/desplegada. |
| **No cambiar tipos incompatibles directamente.** | Pérdida o corrupción de datos. Usar columna auxiliar y migración controlada. |
| **No aplicar migraciones destructivas sin aprobación.** | `02_ARQUITECTURA.md` §12.12. |

## 7.2 Ejemplo de cambio de columna

```sql
-- Release N (expand)
ALTER TABLE products ADD COLUMN list_price_v2 INTEGER;
UPDATE products SET list_price_v2 = list_price;

-- Release N+1 (contract, una vez todo el código usa list_price_v2)
ALTER TABLE products DROP COLUMN list_price;
ALTER TABLE products RENAME COLUMN list_price_v2 TO list_price;
```

# 8. Health checks

## 8.1 Liveness

| Check | Propósito |
|---|---|
| Proceso de Gunicorn responde | Saber si la aplicación está viva. |
| Endpoint `GET /health/live` | Respuesta rápida sin tocar base de datos. |

## 8.2 Readiness

| Check | Propósito |
|---|---|
| Conexión a PostgreSQL | La aplicación puede atender peticiones. |
| Migraciones compatibles | La versión del código coincide con el esquema. |
| Storage de imágenes accesible | Puede leer/escribir imágenes. |
| Endpoint `GET /health/ready` | Devuelve estado agregado de readiness. |

## 8.3 Endpoint de salud

```
GET /health/live  → 200 { status: ok }
GET /health/ready → 200 { status: ok, checks: { db: true, migrations: true, storage: true } }
```

# 10. Rollback

## 10.1 Rollback de aplicación

| Componente | Método |
|---|---|
| Frontend | Restaurar build estático anterior desde artefacto versionado. |
| Backend | Restaurar imagen Docker / código anterior y reiniciar Gunicorn. |
| Nginx | Recargar configuración anterior si cambió. |

## 10.2 Rollback de datos

- **Migraciones reversibles:** aplicar `downgrade` de Alembic.
- **Migraciones irreversibles:** no se hace rollback de BD; se restaura desde backup.
- **Regla:** si una migración destruye datos, requiere aprobación explícita y backup verificado antes de aplicar.

## 10.3 Cuándo NO se hace rollback de BD

- La migración ya fue exitosa y el código nuevo ya escribió datos en el nuevo esquema.
- No existe backup verificado reciente.
- El rollback implicaría pérdida de datos de usuarios (por ejemplo, productos editados tras el despliegue).

---

# 11. Backups

## 11.1 Tipo y frecuencia

| Origen | Tipo | Frecuencia | Retención |
|---|---|---|---|
| PostgreSQL | Dump lógico (`pg_dump`) | Diario | 30 días |
| Imágenes originales | Copia incremental | Diario | 30 días |
| Derivados de imágenes | Regenerables | Semanal | 7 días |

## 11.2 Verificación

- Cada backup se verifica con una restauración en entorno aislado al menos una vez por semana.
- Un backup no verificado no se considera backup (`02_ARQUITECTURA.md` §12.12).

## 11.3 Punto de recuperación esperado

- **RPO (Recovery Point Objective):** máximo 24 horas de pérdida de datos aceptable.
- **RTO (Recovery Time Objective):** 4 horas para restaurar servicio completo en caso de fallo grave.

# 13. Observabilidad post-deploy

Durante los 15–30 minutos posteriores a un despliegue se monitorea:

| Métrica | Umbral de alerta | Herramienta |
|---|---|---|
| Errores 5xx | > 1% de peticiones | Logs estructurados / alerta. |
| Latencia p95 API | > 300 ms (`RNF-02`) | Métricas de aplicación. |
| Errores de conexión a BD | Cualquier pico | Logs. |
| Errores de uploads | > 2% de intentos | Logs. |
| Errores de sesión / login | Cualquier pico | Logs + audit. |
| Errores JavaScript en frontend | Reportados por Sentry o Lighthouse | Punto de extensión. |

---

# 14. Criterio de deploy exitoso

Un despliegue **no es exitoso** solo porque los contenedores están arriba o el health check devuelve 200.

Un despliegue se considera **exitoso** cuando:

- [ ] Migraciones aplicadas sin errores.
- [ ] Health checks liveness y readiness pasan.
- [ ] Smoke tests mínimos pasan.
- [ ] Tasa de errores 5xx dentro del umbral (< 1%).
- [ ] Latencia p95 dentro del umbral (`RNF-02`).
- [ ] Login admin funciona.
- [ ] Catálogo navegable.
- [ ] Revalidación de carrito funciona.

---

# 15. Criterio de rollback automático

Se activa rollback automático si ocurre cualquiera de:

| Condición | Umbral |
|---|---|
| Tasa de errores 5xx | > 5% durante 2 minutos. |
| Readiness falla | > 2 minutos consecutivos. |
| Smoke test crítico falla | Cualquier fallo en login, catálogo o revalidación. |
| Migración incompatible | El código no puede arrancar por discrepancia de esquema. |

# 16. Archivos y storage

## 16.1 Persistencia de imágenes

- Las imágenes originales y derivadas viven en un **volumen persistente fuera del contenedor**.
- **Nunca** dentro de la imagen Docker.
- El contenedor backend monta el volumen en `UPLOAD_FOLDER`.
- Nginx sirve las imágenes directamente desde el volumen (`AD-04`).

## 16.2 Permisos

| Recurso | Usuario | Permisos |
|---|---|---|
| Código fuente | `www-data` / `appuser` | Solo lectura. |
| Volumen de imágenes | `www-data` / `appuser` | Lectura para Nginx; lectura/escritura para backend. |
| Logs | `www-data` / `appuser` | Lectura/escritura. |

---

# 17. Seguridad de despliegue

| Control | Implementación |
|---|---|
| HTTPS obligatorio | Nginx termina TLS. Redirección 80 → 443. |
| HSTS | `Strict-Transport-Security: max-age=31536000; includeSubDomains`. |
| Secretos fuera del repositorio | Variables de entorno o sistema de orquestación (`03_SEGURIDAD.md` §18). |
| Usuario no root | Gunicorn y Nginx ejecutan con usuarios dedicados. |
| Permisos mínimos del volumen | Backend solo escribe en `UPLOAD_FOLDER`; Nginx solo lee. |
| Headers de seguridad | Configurados en Nginx (`03_SEGURIDAD.md` §12). |
| CSP | Política restrictiva (`03_SEGURIDAD.md` §12). |

# 18. Decisiones propuestas

## DPL-01 — Estrategia de despliegue v1: Recreate

| Campo | Valor |
|---|---|
| **Identificador** | `DPL-01` |
| **Decisión** | En v1 se usa despliegue **Recreate**: se detiene el tráfico, se hace backup, se aplican migraciones, se despliega la nueva versión, se verifican health checks y smoke tests, y se habilita tráfico. |
| **Justificación** | Una sola instancia, tráfico predecible, downtime breve aceptable. Blue/Green y Canary son sobredimensión. |
| **Consecuencias** | Ventana de mantenimiento breve. Se planifica fuera de horario comercial. |

## DPL-02 — Entorno de staging intermedio

| Campo | Valor |
|---|---|
| **Identificador** | `DPL-02` |
| **Decisión** | Se implementa un entorno de **staging** con infraestructura similar a producción. |
| **Justificación** | Cierra `AP-01` / `ADP-04`. Permite validar migraciones, rendimiento y smoke tests antes de producción. |
| **Consecuencias** | Costo de infraestructura adicional. Los datos de staging se regeneran desde fixtures. |

## DPL-03 — Backup diario con verificación semanal

| Campo | Valor |
|---|---|
| **Identificador** | `DPL-03` |
| **Decisión** | Backup diario de PostgreSQL e imágenes originales; verificación de restauración semanal. |
| **Justificación** | `RNF-16` y `02_ARQUITECTURA.md` §12.12. Un backup no verificado no es backup. |
| **Consecuencias** | RPO 24h, RTO 4h. |

## DPL-04 — Imágenes en volumen persistente local

| Campo | Valor |
|---|---|
| **Identificador** | `DPL-04` |
| **Decisión** | Las imágenes se almacenan en un volumen persistente local montado en el servidor, no en la imagen Docker ni en S3/Cloudinary en v1. |
| **Justificación** | `AD-05`. S3/Cloudinary queda como punto de extensión. |
| **Consecuencias** | El volumen debe incluirse en el backup y persistir ante redeploys. |

## DPL-05 — Docker Compose para orquestación en v1

| Campo | Valor |
|---|---|
| **Identificador** | `DPL-05` |
| **Decisión** | Se usa **Docker Compose** para orquestar Nginx, Gunicorn, PostgreSQL y volumen de imágenes en producción v1. |
| **Justificación** | Suficiente para una sola instancia. Kubernetes es sobredimensión (`PA-11`). |
| **Consecuencias** | El escalado horizontal manual en v2 requerirá reconsiderar la orquestación. |

## DPL-06 — Logs en archivos estructurados, sin SIEM en v1

| Campo | Valor |
|---|---|
| **Identificador** | `DPL-06` |
| **Decisión** | Los logs se escriben en archivos estructurados JSON en el servidor. No se implementa SIEM en v1. |
| **Justificación** | `OA-09` y `03_SEGURIDAD.md` §15. El volumen de logs no justifica SIEM. |
| **Consecuencias** | Rotación de logs y acceso SSH/SCP para diagnóstico. Punto de extensión para v2. |

## DPL-07 — VPS único con servicios en contenedores

| Campo | Valor |
|---|---|
| **Identificador** | `DPL-07` |
| **Decisión** | Se despliega en un **VPS único** con servicios contenerizados (Nginx, Gunicorn, PostgreSQL). |
| **Justificación** | Reduce complejidad operativa y costo. El tráfico previsto no requiere servicios separados. |
| **Consecuencias** | El escalado vertical tiene límites; migrar a servicios separados es punto de extensión. |
