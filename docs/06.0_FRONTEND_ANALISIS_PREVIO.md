# 2. Objetivo

Este documento es el análisis previo de `06_FRONTEND.md`. **No redacta el documento final**, sino que:

1. Detecta contradicciones con los documentos aprobados.
2. Identifica decisiones pendientes que deben cerrarse antes de la redacción.
3. Mapea casos de uso a features y componentes.
4. Señala dependencias, duplicaciones y vacíos reales.
5. Propone correcciones justificadas sin introducir arquitectura nueva ni modificar decisiones aprobadas.

El resultado debe permitir redactar `06_FRONTEND.md` en una única pasada coherente.

# 3. Estado de decisiones pendientes

## 3.1 AD-07 / ADP-01 — Biblioteca de estado global

| Aspecto | Estado |
|---|---|
| **Decisión original** | `AD-07` (diferida): la arquitectura no depende de una biblioteca global de estado; la elección concreta se delega a `06_FRONTEND.md`. |
| **Pendiente registrado** | `ADP-01`: "Resolución de `AD-07` — biblioteca de estado global" → `06_FRONTEND.md`. |
| **Condición de resolución** | Conocer el volumen real de estado compartido y la frecuencia de actualizaciones. |

**Análisis.** `02_ARQUITECTURA.md` §8.6 clasifica los ámbitos de estado y establece cuatro tipos: local, compartido, persistente y derivado. El único estado persistente y de alta frecuencia de actualización es el **carrito**. Los filtros son derivados de la URL; la sesión y la configuración de tienda son estado del servidor; el tema y las notificaciones son compartidos pero simples.

**Propuesta de resolución (para `06_FRONTEND.md`):**

- **Estado del servidor (server state):** usar **TanStack Query (React Query)**. Cumple `ES-02` ("el estado del servidor no es estado del cliente") porque es caché de lectura, no estado global mutable. No contradice `AD-07`, que se refiere a bibliotecas de estado global del cliente. **El acceso se realiza exclusivamente a través de hooks propios del feature** (`DEP-11`); ningún componente importa `useQuery` o `useMutation` directamente.
- **Estado compartido/persistente del cliente:** usar **Zustand** para el carrito (persistente, actualizaciones frecuentes), tema y notificaciones. Cumple `AD-07` porque el acceso se hace a través de hooks propios (`DEP-11`). Los stores viven en `features/X/stores/` o `shared/stores/` y se consumen mediante hooks como `useCart()`, `useTheme()`.
- **Estado simple compartido:** usar **React Context** para la sesión del administrador, que es un único objeto pequeño y de baja frecuencia de cambio. El acceso también se realiza mediante `useAuth()`.

**Justificación.** Zustand es más liviana que Redux (`PA-11`), no impone repetición estructural como Context para actualizaciones frecuentes del carrito, y mantiene la puerta abierta a cambios futuros gracias a `DEP-11`.

# 5. Análisis sección por sección del documento propuesto

## 5.1 Filosofía del frontend

**Contenido propuesto:** React + Vite, SPA, Mobile First, Feature First, componentes desacoplados.

**Evaluación:**
- React + Vite: aprobado en `00_VISION_PROYECTO.md` §9.
- SPA: aprobado en `AD-01`.
- Mobile First: aprobado en `02_ARQUITECTURA.md` §8.4 (mayormente móvil) y `RNF-06`.
- Feature First: aprobado en `AD-08`.
- Componentes desacoplados: aprobado en `02_ARQUITECTURA.md` §8.3.

**Corrección sugerida:** agregar el principio "el frontend no conoce la base de datos" (`AD-12`) y "el frontend no decide reglas de negocio" (`AD-03`).

## 5.2 Organización del proyecto

**Contenido propuesto:** `features/`, `shared/`, `hooks/`, `services/`, `layouts/`, `pages/`, `assets/`.

**Evaluación:**
- La estructura propuesta es compatible con `AD-08`, pero mezcla conceptos. `02_ARQUITECTURA.md` §8.2 propone:
  ```
  src/
  ├── features/
  ├── shared/
  │   ├── components/
  │   ├── layouts/
  │   ├── hooks/
  │   ├── services/
  │   ├── formatters/
  │   ├── types/
  │   └── config/
  ├── routes/
  └── app/
  ```

**Corrección sugerida:** `pages` no es una carpeta raíz separada; las páginas viven dentro de cada feature (por ejemplo, `features/catalog/pages/CatalogPage.jsx`). `routes/` es la composición. `assets/` puede vivir en `shared/assets/` o a nivel `src/`. `services/` en raíz no debería existir: cada feature tiene su propia capa de servicios; solo el cliente HTTP base vive en `shared/services`.

## 5.3 Routing

**Contenido propuesto:** `/`, `/catalog`, `/product/:slug`, `/search`, `/cart`, `/about`, `/contact`.

**Evaluación:**
- **Contradicción importante:** `02_ARQUITECTURA.md` §8.5 establece que "Las rutas se escriben **en español**: son parte de la interfaz, no del código (`NM-01`)".
- Las rutas propuestas en inglés violan `GL-10` / `NM-01` en la capa visible al usuario.

**Corrección sugerida:**

| Propuesta (inglés) | Corrección (español) | Justificación |
|---|---|---|
| `/` | `/` | Home es aceptable como raíz. |
| `/catalog` | `/catalogo` | `NM-01`: interfaz en español. |
| `/product/:slug` | `/producto/:slug` | `NM-01`, `RN-10`. |
| `/search` | `/catalogo?q=...` | La búsqueda no es una ruta aparte; es un filtro más de `/catalogo` (`02_ARQUITECTURA.md` §11.6). |
| `/cart` | `/carrito` | `NM-01`. |
| `/about` | `/nosotros` | `NM-01`. |
| `/contact` | `/contacto` | `NM-01`. |

**Rutas adicionales necesarias:**
- `/admin/login` y `/admin/*` (protegidas).
- Ruta de categoría limpia: `/categoria/:slug` o `/catalogo/:categoriaSlug` (para SEO, según `02_ARQUITECTURA.md` §8.9).

## 5.4 Gestión del estado

**Contenido propuesto:** decidir Context vs Zustand.

**Evaluación:**
- `AD-07` difería la decisión y `ADP-01` la asigna a `06_FRONTEND.md`.
- `02_ARQUITECTURA.md` §8.6 clasifica el estado en cuatro tipos y distingue estado del servidor (`ES-02`).

**Propuesta de resolución:**

| Tipo de estado | Herramienta | Justificación |
|---|---|---|
| Server state (catálogo, producto, configuración) | **TanStack Query** | Cumple `ES-02`; maneja caché, revalidación y estados de carga/error de forma uniforme. |
| Carrito de consulta (persistente, alta frecuencia) | **Zustand + persist middleware** | Cumple `AD-07` vía hook propio; más eficiente que Context para actualizaciones frecuentes. |
| Tema, notificaciones (compartido simple) | **Zustand** o **Context** | Zustand unifica el acceso; Context también es válido. |
| Sesión del administrador (compartido simple) | **Context** | Un solo objeto pequeño; cookie manejada por el navegador. |
| Filtros | **Derivado de la URL** | `ES-05`, `RF-06`. No requieren biblioteca de estado. |
| Total estimado, cantidad de ítems | **Derivado** | `ES-01`. Se calculan a partir del carrito. |

## 5.5 Comunicación con la API

**Contenido propuesto:** cliente HTTP, interceptores, manejo uniforme de errores, retries, timeouts.

**Evaluación:**
- `02_ARQUITECTURA.md` §8.7 define la capa de servicios y el cliente HTTP.
- `05_API.md` §4.3 define la envoltura uniforme `success/data/errors/meta`.
- `AD-16` y `AD-13` definen el formato de errores.

**Correcciones sugeridas:**
- El cliente HTTP base vive en `shared/services/httpClient.js`.
- Los interceptores manejan: credenciales de sesión en rutas privadas, identificador de correlación (`OA-09`), normalización de errores y redirección a `/admin/login` ante `401`.
- Retries: solo para errores de red (`GET` idempotentes); nunca para `POST /cart/revalidate` ni escrituras del panel.
- Timeouts: definir por tipo de petición (catálogo < 300 ms objetivo `RNF-02`, revalidación con timeout mayor por ser crítica).

## 5.6 Carrito

**Contenido propuesto:** LocalStorage, versionado, sincronización entre pestañas, revalidación, construcción del mensaje, apertura de WhatsApp.

**Evaluación:**
- Todo está definido en `02_ARQUITECTURA.md` §13 y en `05_API.md` §8.
- La estructura del carrito debe incluir: versión de formato, versión de contenido, fecha de última modificación, e ítems con `variant_id`, cantidad y copia de datos mostrables (`02_ARQUITECTURA.md` §13.2).

**Correcciones sugeridas:**
- La revalidación ocurre en **dos momentos**: al abrir el carrito y antes de generar el mensaje (`RN-56`, `DN-10`).
- La construcción del mensaje usa las plantillas de `store_settings` (`RF-41`), no texto hardcodeado.
- El control de longitud del mensaje es obligatorio antes de abrir WhatsApp (`RN-76`, `DN-17`).
- El código de consulta `PS-XXXXX` se genera en el cliente (`RN-64`).

## 5.7 Componentes reutilizables

**Contenido propuesto:** ProductCard, ProductGrid, ProductGallery, FiltersPanel, SearchBar, Pagination, Badge, Price, Banner.

**Evaluación:**
- Son componentes naturales derivados de los casos de uso y DTOs.
- No hay contradicciones con documentos aprobados.
- Deben vivir en `features/X/components/` o promoverse a `shared/components/` cuando dos o más features los usen (`DEP-12`).

**Corrección sugerida:** diferenciar componentes de presentación (sin lógica de API) de componentes conectados (que usan hooks del feature). Documentar que `Price` no calcula reglas de negocio; solo formatea guaraníes y aplica estilos según `sale_price` / `discount_percentage` del DTO.

## 5.8 Accesibilidad

**Contenido propuesto:** teclado, foco, aria, contraste, lectores de pantalla.

**Evaluación:**
- No hay decisiones arquitectónicas previas sobre accesibilidad, pero es un requisito transversal coherente con la calidad del proyecto.
- No contradice nada aprobado.

**Sugerencia:** vincular con `RNF-07` (alcanzar cualquier producto en pocas interacciones) y definir un nivel objetivo (por ejemplo, WCAG 2.1 AA como aspiración, con cumplimiento mínimo de navegación por teclado y etiquetas ARIA).

## 5.9 Rendimiento

**Contenido propuesto:** lazy loading, code splitting, imágenes, memoización, virtualización.

**Evaluación:**
- `02_ARQUITECTURA.md` §8.10 ya define la estrategia de rendimiento.
- **Contradicción potencial:** la virtualización está explícitamente descartada en v1 (`02_ARQUITECTURA.md` §8.10: "Virtualización de listas: No en v1").

**Corrección sugerida:** documentar que la virtualización es un punto de extensión, no una técnica de v1. La paginación acota el tamaño de las listas.

## 5.10 SEO

**Contenido propuesto:** HTML para bots, React para usuarios.

**Evaluación:**
- `AD-09` y `02_ARQUITECTURA.md` §8.9 definen la estrategia.
- `05_API.md` §6 documenta los endpoints HTML para rastreadores (`/_seo/products/{slug}`, `/_seo/categories/{slug}`, `/_seo/catalog`).

**Corrección sugerida:** el frontend no genera el HTML para bots; Nginx deriva a los endpoints SEO del backend. El frontend solo debe asegurar que los metadatos dinámicos de React (para Google) y los enlaces canónicos sean correctos.

## 5.11 Responsive

**Contenido propuesto:** breakpoints, grids, imágenes, navegación.

**Evaluación:**
- Mobile First es el enfoque aprobado.
- No hay contradicciones.

**Sugerencia:** vincular con Bootstrap 5.3 (aprobado en `00_VISION_PROYECTO.md`) como base del sistema de grids, pero documentar que los componentes críticos (tarjetas de producto, galería) pueden necesitar ajustes específicos.

## 5.12 Testing Frontend

**Contenido propuesto:** qué se probará, qué no, relación con `11_TESTING.md`.

**Evaluación:**
- `11_TESTING.md` aún no existe.
- Es correcto dejar la estrategia de testing frontend para `11_TESTING.md`, pero `06_FRONTEND.md` debe definir los **tipos de prueba que afectan el diseño** (por ejemplo, componentes con estados de carga/error, flujo del carrito, manejo de errores de la API).

**Sugerencia:** en `06_FRONTEND.md` documentar que el testing detallado se define en `11_TESTING.md`, pero listar los flujos críticos del frontend que deberán ser probados.

# 6. Contradicciones detectadas

## 6.1 Contradicción C-01: Rutas públicas en inglés

- **Documento aprobado:** `02_ARQUITECTURA.md` §8.5: "Las rutas se escriben **en español**: son parte de la interfaz, no del código (`NM-01`)."
- **Propuesta inicial:** `/catalog`, `/product/:slug`, `/search`, `/cart`, `/about`, `/contact`.
- **Corrección:** usar rutas en español: `/catalogo`, `/producto/:slug`, `/carrito`, `/nosotros`, `/contacto`. La búsqueda no es ruta aparte, sino `/catalogo?q=...`.
- **Impacto:** medio. Cambia URLs visibles al usuario y debe ser consistente en todo el frontend.

## 6.2 Contradicción C-02: Estructura de carpetas con `pages/` y `services/` en raíz

- **Documento aprobado:** `02_ARQUITECTURA.md` §8.2: feature-first con páginas dentro de cada feature; servicios del feature dentro del feature; solo el cliente HTTP base en `shared/`.
- **Propuesta inicial:** `pages/` y `services/` como carpetas raíz.
- **Corrección:** páginas dentro de `features/X/pages/`, servicios dentro de `features/X/services/`, cliente HTTP base en `shared/services/`.
- **Impacto:** bajo. Es una reorganización interna.

## 6.3 Contradicción C-03: Virtualización en v1

- **Documento aprobado:** `02_ARQUITECTURA.md` §8.10: "Virtualización de listas: **No en v1**."
- **Propuesta inicial:** mencionar virtualización como técnica de rendimiento.
- **Corrección:** documentarla como **punto de extensión**, no como técnica activa de v1.
- **Impacto:** bajo.

## 6.4 Inconsistencia leve I-01: Componente `SearchBar` con ruta propia

- **Documento aprobado:** `02_ARQUITECTURA.md` §11.6: "La búsqueda es **un filtro más**, no un endpoint aparte: `?q=botin`."
- **Propuesta inicial:** ruta `/search`.
- **Corrección:** la búsqueda se realiza en `/catalogo?q=...`. No existe ruta `/search`.
- **Impacto:** bajo.
