# 2. Objetivo

Este documento es el análisis previo de `11_TESTING.md`. **No redacta el documento final**, sino que:

1. Define la estrategia general de pruebas del proyecto.
2. Establece la pirámide de pruebas y el alcance de cada tipo.
3. Define la trazabilidad obligatoria entre elementos aprobados (`RN-xx`, `RF-xx`, `RNF-xx`, `AD-xx`, `BK-xx`, `UDS-xx`, `COMP-xx`) y casos de prueba.
4. Mapea cada documento aprobado a los tipos de prueba que lo validan.
5. Identifica casos críticos, datasets de prueba, entornos, rendimiento, seguridad y automatización.
6. Propone una Definition of Done y una política de cobertura basada en riesgo.
7. Documenta la verificación obligatoria de esquemas antes de dar una tarea por finalizada.

El resultado debe permitir redactar `11_TESTING.md` en una única pasada coherente, sin introducir decisiones arquitectónicas ni reglas de negocio nuevas.

# 3. Estrategia general

## 3.1 Propósito de `11_TESTING.md`

`11_TESTING.md` debe ser la **autoridad única** sobre qué se prueba, cómo se prueba, dónde se prueba y cuándo una funcionalidad tiene evidencia suficiente de calidad. No reemplaza los contratos de API ni las reglas de negocio; los hace verificables.

## 3.2 Alcance de las pruebas en v1

| Incluye | No incluye (fuera de alcance v1) |
|---|---|
| Pruebas unitarias, de integración, de contrato de API, E2E, de seguridad, de rendimiento, de accesibilidad, de smoke y de regresión. | Pentesting profesional (`03_SEGURIDAD.md` §3.3). |
| Validación de `RN-xx`, `RF-xx`, `RNF-xx`, `AD-xx`, `BK-xx`. | Tests de carga masiva o estrés a escala industrial. |
| Flujos críticos del catálogo, carrito, panel y seguridad. | Moderación automática de contenido de imágenes. |
| Verificación de esquema local vs. producción. | Tests de recuperación ante desastres (DR). |
| T-ADP07-08: verificación en dispositivo real de WhatsApp. | |

## 3.3 Relación con el Architecture Freeze

`02_ARQUITECTURA.md` v1.0.0 está congelado. `11_TESTING.md` no introduce arquitectura nueva; solo define cómo verificar las decisiones aprobadas. Si una prueba revela que una decisión `AD-xx` no es verificable, se registra como pendiente arquitectónico.

# 4. Pirámide de pruebas

```
            /
           /  \         E2E / Aceptación manual
          /____\
         /      \       Contrato de API
        /________\
       /          \     Integración
      /____________\
     /              \   Unitarias / Componentes
    /________________\
```

| Nivel | Tipo | Propósito | Velocidad | Cantidad |
|---|---|---|---|---|
| **Base** | Unitarias / Componentes | Validar funciones, hooks, componentes, mappers, validators, schemas de forma aislada. | Muy rápido | Muchas |
| **Media baja** | Integración | Validar combinaciones de capas (servicio + repositorio + base de datos). | Rápido | Moderadas |
| **Media alta** | Contrato de API | Validar request/response de `05_API.md` sin base de datos compleja. | Rápido | Moderadas |
| **Cima** | E2E / Manuales | Validar flujos completos del usuario. | Lento | Pocas |

## 4.1 Tipos de prueba por nivel

| Tipo | Descripción | Ejemplo en Pablito Sports |
|---|---|---|
| **Unitarias** | Funciones puras, clases y métodos aislados. | `PriceValidator`, `ProductMapper`, `useCart`. |
| **Componentes** | Renderizado e interacciones de componentes React. | `ProductCard`, `VariantSelector`, `ConfirmDialog`. |
| **Integración** | Combinación de varias unidades o capas del backend con base de datos real. | `ProductService` + `ProductRepository` + PostgreSQL. |
| **Contrato de API** | Verificar que la API cumple `05_API.md`: status, envoltura, DTOs, errores. | No requiere base de datos compleja; puede usar mocks de servicios. |
| **End-to-End (E2E)** | Flujo completo desde la interfaz hasta el backend. | Consulta por WhatsApp: catálogo → carrito → mensaje. |
| **Manuales de aceptación** | Validación humana de criterios de negocio. | Revisión visual de producto destacado en homepage. |
| **Smoke tests** | Verificación rápida de que lo esencial funciona. | Login, lista de productos, detalle, carrito. |
| **Regresión** | Conjunto de pruebas que se ejecutan ante cambios. | Suite completa antes de cada merge a `main`. |

## 4.2 Matriz de criticidad

Priorización por impacto para decidir qué probar primero bajo presión.

| Área | Criticidad | Cobertura mínima |
|---|---|---|
| Revalidación del carrito | 🔴 Alta | Unit + Integration + API Contract + E2E |
| Autenticación admin | 🔴 Alta | Integration + Security + E2E |
| Autorización y permisos | 🔴 Alta | Integration + Security + E2E |
| Promociones / precio efectivo | 🔴 Alta | Unit + Integration |
| Soft delete y restauración | 🔴 Alta | Integration + API Contract |
| Auditoría | 🔴 Alta | Integration + E2E |
| Filtros y búsqueda de catálogo | 🟡 Media | Unit + Integration + API Contract |
| SEO / metadatos para rastreadores | 🟡 Media | Integration + Manual |
| Subida y procesamiento de imágenes | 🟡 Media | Integration + Security |
| Banners | 🟢 Baja | Integration |
| Configuración de tienda | 🟢 Baja | Integration + API Contract |

## 4.3 Reglas de regresión

**TEST-REG-01.** Toda corrección de un bug debe incluir una prueba de regresión que **falle antes del fix y pase después del fix**. La prueba se incorpora a la suite permanente del proyecto.

**TEST-REG-02.** Antes de cada merge a `main`, la suite de regresión completa debe ejecutarse sin fallos.

**TEST-REG-03 — Aislamiento temporal.** Los tests no deben depender de la fecha/hora real del sistema. Se utilizará reloj controlado o fixtures de tiempo congelado. Queda prohibido usar `now()` directamente en aserciones.

## 4.4 Política de estabilidad de tests (flaky tests)

| Aspecto | Regla |
|---|---|
| **Definición** | Un test con tasa de fallo intermitente > 2% en 30 ejecuciones se considera flaky. |
| **Bloqueo de releases** | Un flaky test no puede bloquear un release sin ticket de corrección asociado. |
| **Remediación** | Se registrará causa raíz, acción correctiva y fecha objetivo de remediación. |
| **Prevención** | Evitar sleeps fijos, dependencias de orden, datos compartidos entre tests y condiciones de carrera. |

# 5. Trazabilidad obligatoria

Todo elemento aprobado debe tener evidencia verificable. La trazabilidad se expresa como: **elemento → caso(s) de prueba → tipo de prueba → criterio de aceptación**.

| Prefijo | Elemento | Evidencia esperada |
|---|---|---|
| `RN-xx` | Regla de negocio | Al menos un test unitario o de integración que demuestre su cumplimiento y su violación. |
| `RF-xx` | Requisito funcional | Al menos una prueba funcional (integración, E2E o manual) que recorra el caso de uso. |
| `RNF-xx` | Requisito no funcional | Método de medición reproducible + criterio de aceptación numérico. |
| `AD-xx` | Decisión arquitectónica | Prueba cuando sea verificable (por ejemplo, `AD-37` mediante tests de sesión). |
| `BK-xx` | Decisión de implementación backend | Tests que validen la estructura de capas y las prohibiciones (`DEP-01`–`DEP-07`). |
| `UDS-xx` / `COMP-xx` | Tokens o componentes del UI System | Pruebas visuales o de componentes cuando corresponda. |

**Regla.** Si un `RN-xx` no tiene al menos un caso de prueba asociado, la funcionalidad correspondiente no puede darse por implementada.

# 9. Datos de prueba

Se definen datasets reproducibles bajo `tests/fixtures/`:

| Dataset | Contenido mínimo |
|---|---|
| **Usuarios** | Administrador, superadministrador, usuario inactivo. |
| **Productos** | Producto activo, inactivo, eliminado, destacado, nuevo, en oferta, sin stock. |
| **Variantes** | Variante activa, eliminada, con combinaciones de color/talle. |
| **Promociones** | Promoción vigente, vencida, futura, por producto/categoría/marca. |
| **Banners** | Banner activo, vencido, en posición específica. |
| **Imágenes** | Archivos válidos (jpg, png, webp) e inválidos (pdf, exe, gif animado). |
| **Carrito** | Carrito vacío, con ítems válidos, con ítems obsoletos, con 26 ítems (`RN-75`). |
| **Auditoría** | Registros de escritura del panel. |
| **Historial de precios** | Cambios de precio con administrador y fecha. |

**Reglas.**

1. Los fixtures se cargan mediante semillas o factories, nunca con datos de producción.
2. Cada test arranca con un estado conocido y lo limpia al final.
3. Las imágenes de prueba viven en `tests/fixtures/images/` y son pequeñas (< 50 KB).

### IDs de semilla congelados

Para evitar tests frágiles, los seeds de testing declaran IDs estables e inmutables:

| Entidad | ID | Slug |
|---|---|---|
| Administrador base | `ADMIN_ID = 1` | — |
| Superadministrador | `SUPER_ADMIN_ID = 2` | — |
| Marca Nike | `BRAND_NIKE_ID = 1` | `nike` |
| Categoría Botines | `CATEGORY_BOTINES_ID = 1` | `botines` |
| Género Unisex | `GENDER_UNISEX_ID = 1` | `unisex` |
| Tipo de talle numérico | `SIZE_TYPE_NUMERIC_ID = 1` | `footwear_numeric` |
| Producto base | `PRODUCT_BASE_ID = 1` | `botin-nike-mercurial` |
| Variante base | `VARIANT_BASE_ID = 1` | — |

> **Regla.** Los seeds de testing son inmutables. Un cambio de ID requiere actualizar todos los tests que lo referencian y se considera cambio estructural.

# 11. Rendimiento

| Requisito | Métrica | Método |
|---|---|---|
| `RNF-01` | LCP < 2,5 s en 4G | Lighthouse CI o WebPageTest; throttling 4G; 5 repeticiones; p95. |
| `RNF-02` | API de catálogo < 300 ms (p95) | `pytest` + `EXPLAIN ANALYZE`; entorno staging; dataset de 2.000 productos, 10 marcas, 15 categorías; 5 repeticiones; p95. |
| `RNF-03` | Imágenes optimizadas y con lazy loading | Lighthouse + inspección de markup; verificar formatos WebP y atributo `loading="lazy"`. |
| `RNF-07` | Todo producto alcanzable en ≤ 3 interacciones | E2E en viewport 390 px. |
| Facetas | p95 de consulta con facetas < 300 ms | Staging; 2.000 productos; 5 repeticiones; p95. |
| Revalidación del carrito | < 300 ms con 26 ítems | Prueba de integración con fixture de 26 ítems; 5 repeticiones; p95. |

### Método de medición estándar

| Elemento | Valor |
|---|---|
| **Entorno** | Staging con infraestructura similar a producción. |
| **Dataset** | 2.000 productos activos, 10 marcas, 15 categorías, 5 deportes, 30 talles, 20 colores. |
| **Herramienta** | `pytest-benchmark` / `locust` para backend; Lighthouse CI para frontend. |
| **Iteraciones** | Mínimo 5 por escenario. |
| **Métrica** | Percentil 95 (p95). |
| **Cálculo del p95** | Sobre el conjunto total de observaciones (`n = repeticiones × requests`), no sobre promedios de cada repetición. |
| **Criterio de disparo** | Si p95 supera el umbral, se mide, se identifica el cuello de botella y se decide índice u optimización (`AD-35`). |

**Reglas.**

1. Las pruebas de rendimiento se ejecutan en staging, no en CI, para evitar fluctuaciones.
2. Cada índice nuevo debe justificarse con una medición (`AD-35`).
3. Si el p95 supera el umbral, se documenta el plan de mitigación antes de release.

# 13. Definition of Done

Una funcionalidad se considera terminada cuando cumple, como mínimo:

- [ ] Documentación actualizada (`10_BACKEND.md`, `06_FRONTEND.md`, etc. según corresponda).
- [ ] Pruebas unitarias que cubren las reglas de negocio (`RN-xx`).
- [ ] Pruebas de integración para flujos que cruzan capas.
- [ ] Contratos de API validados (si expone endpoints).
- [ ] Sin regresiones: la suite completa de CI pasa.
- [ ] Revisión de código aprobada.
- [ ] Esquema local verificado contra producción (si aplica cambio de base de datos).
- [ ] Auditoría verificada para operaciones críticas del panel: cambio de precio, eliminación lógica, restauración, cambio de contraseña, publicación de banner (`AD-20`).

# 14. Automatización en CI

## 14.1 Pipeline obligatoria (bloquea merge)

Se ejecuta en cada push/PR:

| Paso | Herramienta sugerida |
|---|---|
| Lint | ESLint (frontend), Flake8/Ruff (backend). |
| Type checking | TypeScript (`tsc`). |
| Unit tests | Jest / Vitest (frontend), pytest (backend). |
| Integration tests | pytest + testcontainers (backend), React Testing Library (frontend). |
| API contract tests | pytest + Flask test client + esquemas de `05_API.md`. |
| Cobertura | cobertura de pytest / Vitest coverage. |
| Build | Vite build, Docker build backend. |

## 14.2 Pipeline opcional / nightly

No bloquea merge; se ejecuta programadamente o antes de release:

| Paso | Herramienta sugerida | Frecuencia |
|---|---|---|
| E2E completo | Playwright / Cypress | Nightly o antes de release. |

| Smoke tests en staging | Scripts de salud | Post-despliegue a staging. |

# 15. Cobertura basada en riesgo

No se fija un porcentaje arbitrario global. En su lugar:

| Elemento | Cobertura esperada |
|---|---|
| Reglas de negocio (`RN-xx`) | 100% deben tener al menos un caso de prueba. |
| Servicios críticos | Todos los métodos públicos con lógica de negocio. |
| Endpoints públicos y administrativos | Todos deben tener pruebas de contrato. |
| Correcciones de bugs | Cada fix debe incluir una prueba de regresión. |
| Mappers y validators | Cobertura alta (> 80%) por ser lógica pura. |
| Componentes compartidos | Cobertura de estados y eventos principales. |

**Métrica de cobertura objetivo (orientativa).**

- Backend servicios: ≥ 80%.
- Backend repositorios: ≥ 70%.
- Frontend utilidades/hooks: ≥ 80%.
- Frontend componentes: ≥ 70%.

La cobertura numérica no sustituye la trazabilidad con `RN-xx`.

# 16. Verificación de esquemas

Se mantiene la regla ya utilizada durante todo el proyecto:

> Antes de considerar completa cualquier modificación que afecte el esquema de la base de datos, debe verificarse que los esquemas de desarrollo/local y producción sean equivalentes mediante migraciones y comparación estructural.

**Proceso:**

1. Generar migración con Alembic.
2. Aplicar `upgrade` en entorno local.
3. Ejecutar tests de integración.
4. Comparar esquema local contra producción (estructura + índices + constraints).
5. Solo después, considerar la tarea finalizada.

> **Regla.** La comparación de esquemas debe realizarse mediante migraciones aplicadas y comparación estructural; **no se considera válida una verificación visual manual**.

**Elementos verificados.**

- Columnas, tipos y nullable.
- Claves primarias y foráneas.
- Constraints (`CHECK`, `UNIQUE`).
- Índices y índices parciales.
- Semillas obligatorias.

**Criterio de aprobación de release.** Una release no se considera aprobada si existen divergencias entre los esquemas de local, CI, staging y producción.
