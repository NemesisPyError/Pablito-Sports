# 2. Objetivo

Definir, **antes de redactar** `09_COMPONENTES.md`, el contrato de implementación de los componentes React de Pablito Sports: clasificación, nivel de reutilización, API uniforme, dependencias, composición, estados, accesibilidad y relación con el sistema de diseño.

`09_COMPONENTES.md` será la **referencia única** de los componentes React del proyecto. No definirá el sistema visual —eso corresponde a `08_UI_SYSTEM.md`— sino cómo se construyen, combinan y reutilizan las piezas de la interfaz.

# 3. Decisiones propuestas

## COMP-01 — `09_COMPONENTES.md` es el contrato de implementación de componentes

| Campo | Valor |
|---|---|
| **Identificador** | COMP-01 |
| **Título** | `09_COMPONENTES.md` es el contrato único entre el UI System y el código React |
| **Contexto** | Sin un contrato común, cada desarrollador implementa componentes con APIs distintas, props inconsistentes y dependencias no documentadas. |
| **Decisión** | Todo componente React del proyecto se documenta en `09_COMPONENTES.md` con un formato uniforme: nombre, propósito, props, eventos, estados, accesibilidad, dependencias, tokens, casos de uso y prohibiciones. |
| **Consecuencias** | La implementación de cualquier componente es predecible. Los agentes de IA y los desarrolladores siguen el mismo patrón. |

## COMP-02 — Todo estilo deriva de `08_UI_SYSTEM.md`

| Campo | Valor |
|---|---|
| **Identificador** | COMP-02 |
| **Título** | Los componentes no definen estilos; consumen tokens del sistema de diseño |
| **Contexto** | `08_UI_SYSTEM.md` ya fue aprobado como autoridad visual única. Los componentes deben respetar esa autoridad. |
| **Decisión** | Ningún componente declara colores, tamaños, espaciados, radios ni sombras directamente. Todos los valores visuales se referencian mediante tokens de `08_UI_SYSTEM.md`. |
| **Consecuencias** | `09_COMPONENTES.md` documenta qué tokens usa cada componente, nunca valores concretos. |

## COMP-03 — Jerarquía de reutilización

| Campo | Valor |
|---|---|
| **Identificador** | COMP-03 |
| **Título** | Todo componente tiene un nivel de reutilización explícito |
| **Contexto** | Sin clasificación, componentes específicos de una página terminan en `shared/` y viceversa. |
| **Decisión** | Cada componente se etiqueta como `Global`, `Feature` o `Page`. La ubicación en el árbol de carpetas debe coincidir con ese nivel. |
| **Consecuencias** | Se evita la promoción incorrecta de componentes. La organización por features de `02_ARQUITECTURA.md` se respeta. |

## COMP-04 — Separación Presentational / Container

| Campo | Valor |
|---|---|
| **Identificador** | COMP-04 |
| **Título** | Todo componente se clasifica como Presentational o Container/Smart |
| **Contexto** | Mezclar componentes que solo renderizan con componentes que gestionan lógica dificulta las pruebas y la reutilización. |
| **Decisión** | **Presentational:** reciben props y renderizan UI. No contienen lógica de negocio ni acceden a estado global. **Container/Smart:** orquestan datos, estado y efectos; pueden usar hooks propios del feature. |
| **Consecuencias** | Los componentes presentacionales son altamente reutilizables y fáciles de probar. Los containers concentran la lógica de integración. |

## COMP-05 — Estabilidad de la API

| Campo | Valor |
|---|---|
| **Identificador** | COMP-05 |
| **Título** | Cada componente declara el estado de estabilidad de su API |
| **Contexto** | Sin esta etiqueta, los cambios en componentes compartidos pueden romper consumidores sin advertencia. |
| **Decisión** | Todo componente documenta su estabilidad: `Stable` (API consolidada), `Internal` (uso restringido al feature), `Experimental` (puede cambiar). |
| **Consecuencias** | Los desarrolladores saben qué componentes pueden usar con confianza y cuáles requieren precaución. |

# 4. Clasificación de componentes

## 4.1 Por responsabilidad

| Categoría | Componentes | Descripción |
|---|---|---|
| **Foundation** | `Button`, `Icon`, `Typography`, `Badge`, `Tag` | Bloques visuales atómicos sin lógica de negocio. |
| **Form** | `Input`, `Select`, `Checkbox`, `Radio`, `Switch`, `Textarea`, `DatePicker`, `FileInput`, `SearchInput`, `FormSection` | Controles de entrada de datos. |
| **Feedback** | `Alert`, `Toast`, `Spinner`, `Skeleton`, `LoadingOverlay`, `ProgressBar`, `EmptyState`, `ErrorState`, `NoPermissionState` | Comunicación de estado al usuario. |
| **Overlay** | `Modal`, `Drawer`, `ConfirmDialog`, `Popover`, `Tooltip` | Elementos que se superponen al contenido. |
| **Navigation** | `Breadcrumb`, `Pagination`, `Tabs`, `Sidebar`, `Navbar`, `Link` | Navegación y orientación. |
| **Data Display** | `Card`, `Table`, `DataTable`, `DataGrid`, `Avatar`, `Image`, `ImageGallery`, `ImageUploader`, `WhatsAppSummary`, `PriceBadge`, `PromotionBadge`, `AvailabilityBadge` | Presentación de datos e información. |
| **Layout** | `Container`, `Stack`, `Grid`, `Section`, `PageHeader`, `Divider` | Estructura y disposición espacial. |
| **Domain (Catálogo)** | `ProductCard`, `ProductGrid`, `ProductGallery`, `ProductFilters`, `ProductSearch`, `FiltersPanel`, `VariantSelector`, `ColorSelector`, `SizeSelector`, `CartDrawer`, `CartItem`, `WhatsAppButton` | Componentes específicos del catálogo público. |
| **Domain (Panel)** | `AdminDataTable`, `AuditTable`, `HistoryTimeline`, `StatusBadge`, `VariantMatrix`, `ImageReorder`, `WhatsAppTemplateEditor`, `PriceHistoryWidget` | Componentes específicos del panel administrativo. |

## 4.2 Por nivel de reutilización

| Nivel | Ubicación | Criterio | Ejemplos |
|---|---|---|---|
| **Global** | `shared/components/` | Usado por al menos dos features o por el sistema de diseño. | `Button`, `Input`, `Modal`, `DataTable`, `Toast` |
| **Feature** | `features/X/components/` | Usado solo dentro de un feature. | `ProductCard`, `CartDrawer`, `AdminDataTable` |
| **Page** | `features/X/pages/` o subcarpeta | Usado en una única página. | `CatalogPage`, `ProductEditPage`, `DashboardPage` |

# 5. Contrato uniforme de componente

Cada componente documentado en `09_COMPONENTES.md` seguirá esta estructura de 17 campos:

| Sección | Contenido |
|---|---|
| **Nombre** | Nombre en inglés, `PascalCase`. |
| **Nivel** | `Global` / `Feature` / `Page`. |
| **Categoría** | Foundation, Form, Feedback, Overlay, Navigation, Data Display, Layout, Domain. |
| **Tipo** | `Presentational` / `Container`. |
| **Estabilidad** | `Stable` / `Internal` / `Experimental`. |
| **Complejidad** | `Baja` / `Media` / `Alta`. |
| **Prioridad** | `P0` / `P1` / `P2`. |
| **Propósito** | Una oración sobre qué hace y cuál problema resuelve. |
| **Props** | Lista de propiedades, tipo, obligatoriedad, valor por omisión y descripción. |
| **Eventos** | Callbacks que expone el componente. |
| **Estados** | Estados visuales que aplica. Hace referencia al estándar del UI System; solo documenta excepciones. |
| **Accesibilidad** | Keyboard, ARIA, Focus, Screen Reader. |
| **Dependencias** | Componentes, hooks, servicios, DTOs o bibliotecas de los que depende. |
| **Usado por** | Componentes que consumen este componente. |
| **Composición** | Qué componentes puede contener y cuáles no. |
| **Tokens utilizados** | Lista de tokens de `08_UI_SYSTEM.md` que consume. |
| **Casos de uso** | Dónde se utiliza en el proyecto. |
| **Prohibiciones** | Qué no debe hacer el componente. |

# 6. Estados visuales estándar

En lugar de repetir estados en cada componente, `09_COMPONENTES.md` referenciará el estándar de `08_UI_SYSTEM.md` §9:

- Default
- Hover
- Focus
- Active
- Disabled
- Loading
- Error
- Success

Cada componente solo documentará excepciones o estados adicionales propios.

# 7. Accesibilidad estándar

Cada componente declarará, cuando aplique:

| Aspecto | Descripción |
|---|---|
| **Keyboard** | Orden de tabulación, atajos, comportamiento con `Enter`/`Escape`/`Space`. |
| **ARIA** | Roles y atributos ARIA requeridos. |
| **Focus** | Gestión del foco, captura en modales, anillo visible. |
| **Screen Reader** | Texto alternativo, anuncios dinámicos, etiquetas. |

## 8.10 Diferenciación `DataTable` vs `DataGrid`

| Aspecto | `DataTable` | `DataGrid` |
|---|---|---|
| **Presentación** | Filas y columnas. | Tarjetas o celdas en grid. |
| **Uso principal** | CRUD del panel, listados administrativos. | Catálogo público, grandes volúmenes. |
| **Volumen esperado en v1** | Hasta ~100 filas por página. | Sin límite estricto; preparado para virtualización futura. |
| **Funciones en v1** | Ordenamiento, paginación, acciones por fila, búsqueda. | Renderizado de tarjetas, paginación. |
| **Virtualización** | No requerida en v1. | Reservada para evolución futura. |

# 10. Componentes prohibidos

Para evitar duplicaciones y fragmentación, los siguientes componentes **NO existirán** en el proyecto:

| Componente prohibido | Razón | Solución |
|---|---|---|
| `PrimaryButton`, `SecondaryButton`, `SuccessButton`, `DangerButton` | Fragmentan un concepto único. | Usar `Button` con prop `variant`. |
| `ProductTable`, `CategoryTable`, `BrandTable`, `UserTable` | Tablas específicas por entidad. | Usar `DataTable` / `AdminDataTable` con configuración de columnas. |
| `ProductSearchBar`, `CategorySearchBar` | Buscadores específicos por entidad. | Usar `SearchInput` o `ProductSearch` genérico. |
| `MobileProductCard`, `DesktopProductCard` | Variantes por viewport. | Usar `ProductCard` con responsive interno. |
| `AdminButton`, `PublicButton` | Botones por contexto. | Usar `Button` con variantes y tokens. |

La regla general es: **si un componente solo cambia por el contexto en el que se usa, debe resolverse mediante props y tokens, no creando un nuevo componente.**
